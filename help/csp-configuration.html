Configuring Content Security Policy (CSP) for GetFeedback

As security and privacy become top priorities, many organizations use a Content Security Policy (CSP) to reduce the risk of XSS (Cross-Site Scripting) attacks and data injection vulnerabilities. A CSP header tells the browser which dynamic resources (such as JavaScript, Stylesheets, and Images) are allowed to execute. If your website uses a strict CSP, you must add GetFeedback to your "allowlist" to ensure your feedback assets load properly.

Optional: Add CSP Hash

If your web infrastructure requires explicit hash-based matching policies, copy the individual values generated inside your platform installation screen and append them directly into your web server response header rules:

  • On script-src: 'sha256-l2ABcDC7VZcirDGllBhNKaAYFYNnOZGjFc6nWjJmnLQ='
  • On style-src: 'nonce-17ddf23a141a'

How to find out if your website uses a CSP

A Content Security Policy is fully public and visible via your client side engine. If you have installed the GetFeedback snippet but your visual components aren't showing or render completely unstyled, you can trace down active rules using three standard discovery methods:

Option 1 - Use developer tools to find a CSP in a response header

  1. Using your choice of browser, open your native developer tools panel and navigate over to the Network layout tab.
  2. Reload your environment and select the primary document file that builds your web page (typically matching your active root domain string).
  3. Verify you are looking at a successful 200 OK response code block, and scroll down into the Response Headers section box.
  4. Scan the headers for a line explicitly named Content-Security-Policy to inspect your operational directives.

Option 2 - Use a 3rd party browser extension to find a CSP in the response header

There are multiple browser extensions available across Chromium-based distribution stores that automatically extract and list active server policies on your active viewport tab.

Security Notice: Be cautious when installing security evaluation extensions inside your workplace browser profile, as some utilities request invasive data access permissions. Verify choices with your IT administrator first.

Option 3 - Use the page source to find a CSP in a meta tag

  1. Open a fresh window tab, navigate to your target production site layout, and right-click any empty white margin area to select View Page Source.
  2. Trigger your browser's page-text search interface panel (using Ctrl + F on Windows, or Cmd + F on macOS layouts).
  3. Search for the precise string tag phrase: "Content-Security-Policy".
  4. If a match is found embedded inline, your policy parameters will follow directly within that element's content attribute.

Resolving Active CSP Console Faults

If a specific CSP error message is showing up inside your browser's diagnostic console view, you can selectively resolve the constraint by appending the appropriate directive category parameters from the comprehensive list below into your system configuration rules:

Required CSP Directives Reference

  • script-src: Authorizes the dynamic core JavaScript engine execution calls required to process and run your interactive survey overlays.
  • img-src: Validates loading permissions for assets, feedback graphics, and user icon elements mapped within your custom asset dashboard themes.
  • style-src: Unlocks stylesheet rendering layers. Note that the asset engine utilizes specific inline variations, which may require you to grant an explicit 'unsafe-inline' bypass value inside this directive section block.
  • frame-src: Allows the secure code iFrame containers to cleanly render on your structural template page margins.
  • connect-src: Permits client-side scripts to run API fetch methods that safely transmit submission feedback payloads back to our data storage servers.
  • font-src: Unblocks typography resource downloads or external asset files (such as Google Fonts) integrated inside your visual interface profiles.

Troubleshooting: Style Restrictions

In highly regulated enterprise networks, technical compliance structures may completely block the inclusion of fallback rules like 'unsafe-inline' within the live style-src directive block.

If your policy strictness forces these exact constraints, take note of the following operational footprint impact:

  • Affected Elements: Your passive Feedback buttons and active questionnaire modules will lose their dynamic styling characteristics (rendering layout blocks as flat, distorted text fields or unformatted broken rows).
  • Unaffected Elements: Automated background behaviors and contextual behavioral campaign logic rules will continue to execute normally behind the scenes.

Alternative Script Workaround

If your engineering infrastructure cannot relax its structural style-src rules to accommodate the tracking snippet, you must configure a manual callback interface. This requires deploying explicit custom hooks to programmatically grab and restyle the native usabilla_live_button_container node element after the core solution has completed initializing on your page tree layout.
